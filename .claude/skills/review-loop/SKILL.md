# レビューループ

引数: `$ARGUMENTS`（1つ目が種別、2つ目以降が対象）

## 準備
1. `docs/guidelines/review.md` を読む。
2. 種別からレビュアーを決める（REV-11）。`plan` → plan-reviewer、`test` → test-reviewer、`code` → code-reviewer。
3. 種別が `code` なら tech.md のテスト・リント・ビルドが成功していること、`test` なら Red（TEST-03）を確認済みであることを確かめる（REV-14）。

## ラウンド（最大3回、REV-05・REV-07）
4. レビュアーのサブエージェントに、対象（ファイルのパス、`code` なら git diff の全文）、関連する REQ・DES の ID、ラウンド番号、`code` なら TASK の `frozen_tests` の一覧だけを渡す。作成の経緯や前ラウンドの議論は渡さない（REV-12）。
5. 返ってきた1行目の件数を読む。ルール ID のない P0・P1、存在しない ID の指摘は無効として除く（REV-04）。
6. 合格（REV-06）なら終了する。
7. 不合格なら、P0 と P1 を修正する。REV-08 の条件に当たる P1 は修正せず保留にし、条件番号と理由を TASK に書く。前ラウンドで修正した箇所に戻す向きの指摘が来たら、条件 (3)（振動）として保留にする。P2 は修正しなくてよい。
8. `test` の場合は修正後に Red を確認し直す（TEST-03）。`code` の場合はテスト・リント・ビルドを再実行する。
9. ラウンドの結果（P0 / P1 / P2 の件数、保留件数）を TASK の作業ログに書く（REV-10）。
10. 3ラウンド目を終えても P0 か保留以外の P1 が残っていれば、修正を止め、残りの指摘の一覧をユーザーに渡して判断を求める（REV-07）。

## 終了時
11. 保留中の P1 があれば一覧にしてユーザーに確認する（REV-09）。
