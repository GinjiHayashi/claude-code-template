# レビューループ

引数: `$ARGUMENTS`（1つ目が種別、2つ目以降が対象）

## 準備
1. この会話でまだ読んでいない（圧縮などで内容が残っていない場合を含む）ときだけ、`docs/guidelines/review.md` を読む。
2. 種別からレビュアーを決める（REV-11）。`plan` → plan-reviewer、`test` → test-reviewer、`code` → code-reviewer。
3. 種別が `code` なら tech.md のテスト・リント・ビルドが成功していること、`test` なら Red（TEST-03）を確認済みであることを確かめる（REV-14）。

## ラウンド（最大3回、REV-05・REV-07）
4. `test` と `code` では、差分を `.claude/review/<TASK-ID>-r<ラウンド番号>.diff` に保存する（REV-12）。`test` はテストファイルの `git diff HEAD`（新しいファイルは `git add -N` してから含める）、`code` は凍結コミット（軽微な変更では変更前のコミット）からの `git diff` とする。
5. レビュアーのサブエージェントに、対象のファイルのパス、差分ファイルのパス、関連する REQ・DES の ID、ラウンド番号、`code` なら TASK の `frozen_tests` の一覧だけを渡す。作成の経緯や前ラウンドの議論は渡さない（REV-12）。
6. 返ってきた1行目の件数を読む。ルール ID のない P0・P1、存在しない ID の指摘は無効として除く（REV-04）。
7. 合格（REV-06）なら終了する。
8. 不合格なら、P0 と P1 を修正する。REV-08 の条件に当たる P1 は修正せず保留にし、条件番号と理由を TASK に書く。前ラウンドで修正した箇所に戻す向きの指摘が来たら、条件 (3)（振動）として保留にする。P2 は修正しなくてよい。P2 を直す場合は、このラウンドの修正に含める（次のラウンドで確認される）。
9. `test` の場合は修正後に Red を確認し直す（TEST-03）。`code` の場合はテスト・リント・ビルドを再実行する。
10. ラウンドの結果（P0 / P1 / P2 の件数、保留件数）を TASK の作業ログに書く（REV-10）。
11. 3ラウンド目を終えても P0 か保留以外の P1 が残っていれば、修正を止め、残りの指摘の一覧をユーザーに渡して判断を求める（REV-07）。

## 終了時
12. 保留中の P1 があれば一覧にしてユーザーに確認する（REV-09）。
13. 合格・上限到達の後は対象を変更しない。残した P2 は TASK の「未解決事項」に書く。それでも変更したら、その差分だけを保存し、同じレビュアーで確認ラウンドを1回行う。P0・P1 が出たら修正を止めてユーザーに渡す（REV-27）。
