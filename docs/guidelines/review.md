# レビュールール

計画書・テストコード・実装コードのレビューに共通するルールの正本である。対象ごとの判定基準は各 guidelines に置き、本ファイルは重要度、終了条件、出力形式、共通観点を定める。

## 重要度

| ID | ルール |
|---|---|
| REV-01 | **P0（重大な欠陥）**: 次のいずれかに当たる指摘。修正するまでマージしない。(1) 要件の受け入れ基準を満たさない (2) 誤った結果、データの破損・消失を起こす (3) セキュリティ上の欠陥がある (4) CLAUDE.md の「重大な落とし穴」に当たるルールに違反する（TEST-03〜05、TEST-12〜19、TEST-21・22、CODE-19、REV-20、DOC-16） (5) 退行を起こす（REV-26） |
| REV-02 | **P1（品質上の問題）**: guidelines のルール ID に違反し、P0 に当たらない指摘。原則として修正する。REV-08 の条件に当たる場合だけ保留できる |
| REV-03 | **P2（改善提案）**: ルール違反ではないが、改善すると読みやすさや保守性が上がる指摘。修正は任意。誤った結果や退行を起こす指摘は P2 にせず、REV-01 の該当する番号で P0 とする |
| REV-04 | P0 と P1 の指摘には、違反したルール ID を必ず書く。ID のない P0・P1、存在しない ID を挙げた指摘は無効とする。P2 のルール ID 欄は `-` とする |

## 終了条件

| ID | ルール |
|---|---|
| REV-05 | 1ラウンドは「レビュー1回」と「その指摘の修正」の組とする |
| REV-06 | **合格**: P0 が0件、かつ保留中を除く P1 が0件になったら終了する。P2 は残っていてよい（Good Enough） |
| REV-07 | **ラウンド上限**: 3ラウンドで終了する。3ラウンド目の後に P0 または保留中以外の P1 が残っていれば、修正を止め、残りの指摘の一覧を人間に渡して判断を求める |
| REV-08 | **P1 の保留**: 次のいずれかに当たる P1 は「人間判定待ち」として保留できる。(1) 修正に要件または設計の変更が必要 (2) 指摘が他のルールや設計と矛盾する (3) 前のラウンドで修正した箇所に、修正を戻す向きの指摘が来た（振動）。保留する場合は、条件番号と理由をタスク記録に書く |
| REV-09 | 終了時に保留中の P1 があれば、一覧にして人間に確認する |
| REV-10 | 各ラウンドの結果（P0 / P1 / P2 の件数、保留件数）をタスク記録の作業ログに書く（DOC-12） |
| REV-27 | **合格後・上限到達後の変更**: 合格（REV-06）またはラウンド上限（REV-07）で終わった後は、対象を変更しない。残した P2 はタスク記録の「未解決事項」に書く。それでも変更する場合は、その差分だけを対象に「確認ラウンド」を1回行う（ラウンド数には数えない）。確認ラウンドで P0 または P1 が出たら、修正を止めて人間に渡す |

## 進め方

| ID | ルール |
|---|---|
| REV-11 | レビューは、対象を作成・修正したエージェントとは別のサブエージェントが行う（計画書: plan-reviewer、テスト: test-reviewer、実装: code-reviewer） |
| REV-12 | 呼び出し側はレビュアーに、対象（ファイルのパスと差分ファイルのパス）、関連する REQ・DES の ID、ラウンド番号、`code` なら TASK の `frozen_tests` だけを渡す。差分は `test` と `code`、および既存の資料を改訂した `plan` で、`.claude/review/<TASK-ID>-r<ラウンド番号>.diff` に保存して渡す（レビュアーは git を実行できないため）。変更要求の計画（WF-18）の `plan` では、影響一覧を書いた TASK も対象に含める。作成時の経緯や前ラウンドの議論は渡さない |
| REV-13 | レビュアーはファイルを修正しない。修正は呼び出し側が行う |
| REV-14 | 機械的な検証はレビューの前に済ませる。コードのレビューはテスト・リント・ビルドがすべて成功した状態で、テストのレビューは Red（TEST-03）を確認した状態で依頼する |

## 出力形式

| ID | ルール |
|---|---|
| REV-15 | 出力の1行目は `判定: 合格 \| P0=n P1=n P2=n` または `判定: 不合格 \| P0=n P1=n P2=n` とする。合格の基準は REV-06 |
| REV-16 | 2行目以降は次の列の表とする。指摘が0件なら「指摘なし」と書く。`\| # \| 重要度 \| 観点 \| ルールID \| 場所 \| 問題 \| 修正案 \|`。場所は `パス:行番号` で書く |
| REV-17 | 出力は日本語の「である調」で書く |

## 共通観点（3つのレビュアーすべてが確認する）

| ID | 観点 | 判定基準 |
|---|---|---|
| REV-18 | SSoT | 同じ情報・同じロジックが2か所以上に書かれていない（DOC-01） |
| REV-19 | 1ファイル1責務 | 1つのファイルが2つ以上の目的を持っていない（DOC-02） |
| REV-20 | 範囲 | 対応する REQ・DES に紐づかない変更が含まれていない |
| REV-21 | 曖昧表現 | 規則・基準・受け入れ基準に判定できない表現がない（DOC-20） |
| REV-22 | 秘密情報 | API キー、パスワード、トークン、個人情報が含まれていない（DOC-19） |
| REV-23 | 開発ルール | 対象に該当する guidelines のルールに違反していない |
| REV-24 | 凍結テスト | code の場合、渡された `frozen_tests` のファイルに差分がない（TEST-04）。差分があれば P0 とする |
| REV-25 | 書式 | フォーマッターが決める項目（CODE-26）は判定の対象外とし、指摘しない。tech.md のフォーマッターが「なし」の場合だけ、空行の個数を CODE-25 で判定する |
| REV-26 | 退行 | 変更前に成功していた既存のテスト、または既存の受け入れ基準を満たしていた入力が、変更後に失敗するか結果が変わることがない。DES の「既存の振る舞いへの影響」（PLAN-20）で変わる・なくなると決めた振る舞いは除く。退行は P0 とする（REV-01 (5)） |

## 対象別の判定基準

レビュアーは独立性のため毎回新しいコンテキストで起動するので、読む範囲を次に限る。

| レビュアー | 読む基準 | 読む資料（project/） |
|---|---|---|
| plan-reviewer | `planning.md`（PLAN-）、`documentation.md`（DOC-） | `glossary.md`。対象が REQ なら `overview.md`、変更要求の TASK なら影響一覧が挙げる REQ・DES・テスト、DES なら `architecture.md` と `test-items.md` の対象 DES の見出し |
| test-reviewer | `testing.md`（TEST-） | `test-items.md` の対象 DES の見出し、対象 DES の「既存の振る舞いへの影響」 |
| code-reviewer | `coding.md`（CODE-）、対応する DES | `architecture.md`、`glossary.md`、`tech.md` の「フォーマッター」と「コメントの書式」 |
