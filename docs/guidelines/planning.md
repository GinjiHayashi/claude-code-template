# 計画ルール

開発開始、要件定義、設計の進め方と、要件・設計の書き方の正本である。plan-reviewer はこのルールで判定する。

## 質問の進め方

| ID | ルール |
|---|---|
| PLAN-01 | ユーザーへの質問は1回に1問とする。選択肢を2〜4個示し、推奨を1つ選んで理由を添える |
| PLAN-02 | 事実（既存のコード、資料、環境の状態）はユーザーに聞かず、自分で調べる。ユーザーに聞くのは判断が必要な事項だけとする |
| PLAN-03 | 記述の矛盾、曖昧な表現（DOC-20）、考慮漏れを見つけたら、指摘して質問する |
| PLAN-04 | 「未定」「わからない」という回答は、その資料の「未決事項」に記録して先に進む（DOC-18） |
| PLAN-18 | 要件定義と設計では、Claude が推奨案で判断して資料を作る。判断ごとに選択肢・採用案・理由を、REQ・DES の「判断」セクションに書く（人間は承認時にここを確認する） |
| PLAN-19 | 要件定義と設計の途中でユーザーに質問するのは、次のどれかに当たる判断だけとする。(1) overview.md・tech.md・REQ から決められず、目的・スコープ・受け入れ基準が変わる (2) 後から戻せない（外部への公開、データの削除・移行、有償サービスの契約など） (3) overview.md・tech.md の記述どうしが矛盾している。質問の形式は PLAN-01 に従う |

## 開発開始（kickoff）

| ID | ルール |
|---|---|
| PLAN-05 | テンプレートの見出しごとに判定する。`（未記入）` が残っている見出しは質問して埋める。記入済みの見出しは、不足・矛盾・考慮漏れの指摘だけを行う |
| PLAN-06 | 空欄の見出しをすべて埋めてから、見出しをまたいだ全体の指摘に進む |
| PLAN-07 | tech.md の「開発コマンド」は、すべての操作に実行可能なコマンドか「なし」が入るまで完了としない |
| PLAN-21 | overview.md に出てくるプロジェクト固有の用語は、開発開始の時点で glossary.md に登録し、「コード上の名前」（英語）を決める。要件のファイル名やコードの名前はこれを使う（DOC-04、CODE-04） |

## 要件（REQ）

| ID | ルール |
|---|---|
| PLAN-08 | 1つの REQ には1つの要件だけを書く。種別（機能 / 非機能）を明記する |
| PLAN-09 | 受け入れ基準は、満たしたかどうかを判定できる形で書く（DOC-20） |
| PLAN-10 | 各 REQ の「根拠」には、overview.md の目的・課題・成功基準のどれに対応するかを書く。非スコープに含まれる要件は作らない |

## 設計（DES）

| ID | ルール |
|---|---|
| PLAN-11 | DES には次をすべて書く。対応要件（REQ の ID と担当する受け入れ基準）、配置（ファイルのパス）、インタフェース（入力・出力・エラー）、データ構造、処理方針、テスト項目への参照。テスト項目そのものは `docs/project/test-items.md` の、その DES の見出しに書く（TEST-08、TEST-11） |
| PLAN-12 | DES にコード本体は書かない |
| PLAN-13 | 対象 REQ の受け入れ基準は、それぞれ1つ以上の DES に割り当てる。各受け入れ基準は、割り当てた DES の test-items.md の項目のどれかで検証する |
| PLAN-14 | 1つの DES は、1回の TDD サイクル（TEST-01）で実装できる大きさにする。作成・変更するファイルが5つを超える場合は分割する。次のファイルは数えない。(1) ツールが生成・更新するもの（ロックファイル、ビルド成果物など） (2) プロジェクトの土台の設定ファイル（パッケージ定義、リンター・フォーマッター・テストツールの設定、`.gitignore`） |
| PLAN-15 | 配置、依存の向き、命名は architecture.md に従う |
| PLAN-20 | 既存のファイルを変更する DES は、処理方針に「既存の振る舞いへの影響」として、保つ振る舞いと変わる振る舞いを書く。変わる振る舞いがあれば、対応する既存テストと受け入れ基準を挙げる（REV-26、TEST-22） |
