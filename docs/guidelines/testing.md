# テストルール

テストの書き方、TDD の進め方、禁止事項の正本である。test-reviewer はこのルールで判定する。テストの実行コマンドは `docs/project/tech.md` に従う。

## TDD の進め方

- **TEST-01** サイクルは設計（DES）1つ単位で回す。1つの DES について次の順で進め、終えてから次の DES に進む。
  1. テストとスタブを書く
  2. Red を確認する
  3. test-reviewer でレビューする
  4. Green
  5. Refactor
  6. code-reviewer でレビューする
- **TEST-02** スタブは DES のインタフェースどおりに作り、呼ばれたら「未実装」のエラーを出す以外の処理を持たせない。スタブは新しく作るインタフェースにだけ置く。既存の関数を変更する場合は、既存の実装を残したまま Red を確認する（TEST-08）。既存の型・関数に引数や項目を足すときは、既存の実装を残し、足した引数・項目に既定値以外が渡されたときだけ「未実装」のエラーを出す（項目を足しただけで新しいテストが成功しないようにするため）
- **TEST-03** **Red**: スタブに対して全テストを実行し、全件が「アサーションの失敗」または「未実装エラー」で失敗することを確認する。DES のインタフェースが「無いとき」の例外を定めている場合（一覧・辞書への登録で、未登録の名前を引くと出る例外など）は、その例外による失敗も Red と認める。構文エラー・import エラーによる失敗は Red と認めない。スタブに対して成功したテストは無効なテストとして書き直す。既存コードを変更する DES は TEST-08 で判定する
- **TEST-04** **凍結**: test-reviewer が合格を出した時点で、その DES のテストファイルだけをコミットし、TASK のフロントマター `frozen_tests` にパスを書いて凍結する。Green と Refactor の間はテストファイルを変更しない。TASK が `in-progress` か `paused` の間は凍結が続く。凍結したファイルへの書き込みは hook が止める（Edit / Write と、典型的な形の Bash の書き込み）
- **TEST-05** 凍結後にテストの誤りを見つけたら、実装を止めてユーザーに報告する。ユーザーの承認後に `frozen_tests` から該当パスを消して (1) に戻り、テストの修正、Red の確認、レビューをやり直す。凍結の解除と承認は作業ログに書く
- **TEST-06** **Green**: 全テスト（既存のテストを含む）を成功させる。リンターとフォーマッターもエラーなしにする
- **TEST-07** **Refactor**: 振る舞いを変えずにコードを整理する。変更のたびに全テストを実行し、成功を保つ
- **TEST-08** **既存コードを変更する DES の Red**: 新しく書いたテストは全件が TEST-03 の理由で失敗し、既存のテストは全件が成功のままであることを確認する。変更前のコードで成功する新しいテストは、test-items.md で「保持」と印を付けた項目（既存の振る舞いが変わらないことの確認）に対応する場合だけ有効とし、それ以外は TEST-03 のとおり無効として書き直す。既存の型・関数に引数や項目を足す DES は、TEST-02 の「足した引数・項目に既定値以外が渡されたときだけ未実装エラーを出す」形にして、新しいテストを失敗させる
- **TEST-09** 既存のテストを削除・変更しない。DES の「既存の振る舞いへの影響」（PLAN-21）で変わると決めた振る舞いのテストだけ変更してよく、なくなると決めた振る舞いのテストだけ削除してよい。例外はテストの整理（TEST-24）だけとする
- **TEST-10** **削除だけの DES**: 新しい振る舞いを持たず、振る舞いを削除するだけの DES は、TEST-01 の (1)〜(3) と凍結（TEST-04）を省く。PLAN-21 で挙げたテストとコードを削除し、全テスト・リント・ビルドを成功させてから (6) の code-reviewer に進む
- **TEST-24** **テストの整理**: 振る舞いを変えず、テストの書き方だけを変える変更（テストファイルをまたぐ補助関数・定数の重複の共通化など）は、`/refactor` の「テストの整理」（RF-40）として、DES を作らずに次の順で行う。Red の代わりに、変更の前後の一致を確かめる。
  1. 変更の前に、全テストが成功することを確かめ、`bash .claude/scripts/test-list.sh save before` でテストの一覧と `DES-xxx #n` の一覧を保存する
  2. テストを書き換える。assert の対象と期待値、テストの名前、テストの説明の `DES-xxx #n` は変えない
  3. 全テストが成功し、`test-list.sh save after` の後の `test-list.sh compare before after` で一覧が一致することを確かめる
  4. test-reviewer で、変更の前後で assert の対象と期待値が変わっていないことを確かめる
  5. 合格したら、変えたテストファイルだけをコミットして凍結する（TEST-04）

## テスト項目

- **TEST-11** テスト項目は `docs/project/test-items.md` の、DES ごとの見出し（`## DES-001 <設計名>`）の下に、次の3分類の表で書く。項目番号は DES の中で3つの表を通して1から振り、欠番を再利用しない。**機械検証**: 入力と期待する出力が決まり、テストコードで合否を判定できるもの。**AI レビュー**: 定性的な判断やコード全体を横断した判断が必要なもの（code-reviewer が CODE ルールで判定する）。**人間確認**: 見た目、使い勝手、業務上の妥当性、自動化できない外部環境に依存するもの
- **TEST-12** 機械検証の項目は、1項目につき1件以上のテストを書く。テストの名前は確かめる振る舞いを表し、DES の ID や項目番号を含めない（例: `rounds_down_to_100_yen`）。DES の ID と項目番号は、テストの説明（関数の説明コメント、テストの説明文字列など）に `DES-001 #1` の形で書く。1つのテストで複数のケースをまとめる（パラメータ化）ときは、各ケースの名前かコメントに項目番号を書く。書き方の例は下の「TEST-12 の書き方の例」
- **TEST-13** 人間確認の項目は、実装の完了時に一覧にしてユーザーに確認を依頼する
- **TEST-14** 公開するインタフェースごとに、次の4種類のケースを機械検証に含める。該当しない種類は、test-items.md の機械検証の表に「該当なし」と理由を書く。**正常系**: 代表的な入力。**異常系**: 不正な入力、エラー条件ごとに1件以上。**境界値**: 最小値、最大値、それぞれの前後、空、ゼロ。**敵対的入力**: 極端に長い入力、特殊文字・制御文字、注入を狙った文字列、null・未定義、想定外の型、重複
- **TEST-15** カバレッジの数値の下限は設けない。網羅性は TEST-12（test-items.md の項目ごとにテストがあること）で確認する

### TEST-12 の書き方の例

言語ごとの例である。ルールは上の TEST-12 であり、形式はこれに限らない。

```python
# pytest: 関数の docstring に書く
def test_rounds_down_to_100_yen():
    """DES-001 #1 1人あたりの額を100円単位に切り捨てる。"""

# パラメータ化: ケースの id に項目番号を入れる
@pytest.mark.parametrize("total, people, expected", [
    pytest.param(10000, 3, 3300, id="DES-001#2 割り切れない"),
    pytest.param(10000, 4, 2500, id="DES-001#3 割り切れる"),
])
def test_per_person_amount(total, people, expected): ...
```

```typescript
// Jest / Vitest: テストの説明文字列に書く
test("DES-001 #1 rounds down to 100 yen", () => { /* ... */ });
test.each([
  [10000, 3, 3300], // DES-001 #2
  [10000, 4, 2500], // DES-001 #3
])("per person amount %i / %i", (total, people, expected) => { /* ... */ });
```

## 禁止事項

- **TEST-16** 常に成功するテストを書かない。アサーションがないテスト、`true` を確認するだけのテスト、期待値をテスト対象の実行結果から計算するテストを含む
- **TEST-17** 実装に、テストの入力を判定して固定値（ダミー値）を返す処理を入れない
- **TEST-18** テストや処理をスキップして成功させない。スキップ指定、特定テストだけの実行指定、条件付きの早期 return、失敗を握りつぶす例外捕捉を含む
- **TEST-19** 期待値を決められるのに、広すぎるアサーション（null でないこと、型、例外が出ないことだけ）で済ませない
- **TEST-20** テスト対象そのものをモックにしない。モックにしてよいのは、テスト対象の外部（ネットワーク、ファイル、時刻、外部サービス）だけとする
- **TEST-21** 現在時刻、乱数、ネットワーク、実行順に依存するテストを書かない。時刻や乱数は外から渡せるようにする
- **TEST-22** テスト同士を依存させない。各テストは単独で実行して同じ結果になる
- **TEST-23** 公開していない内部構造（private な関数や変数）に依存したテストを書かない。インタフェース経由で検証する
- **TEST-25** 2つ以上のテストファイルで使う補助関数・定数は、architecture.md の「ディレクトリ構成」で決めたテストの共通の補助の置き場所に置き、テストファイルに写さない。新しいテストファイルは既存の補助を使う。すでに既存のテストファイルの間にある重複は、その DES では直さず（TEST-09）、`/refactor` のテストの整理（TEST-24）で直す。レビューではこの既存の重複を P2 とする
