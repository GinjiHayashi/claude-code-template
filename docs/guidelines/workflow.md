# ワークフロー

開発の進め方（フェーズの順序、各フェーズの入力・出力・完了条件）の正本である。各フェーズの手順は Skill（`.claude/skills/`）に、判定基準は各 guidelines にある。

## 全体の順序

- **WF-01** 開発は次の順で進める。
  1. 開発開始（`/kickoff`、プロジェクトで1回）
  2. 要件定義（`/plan-spec`、全要件と実装順を決める。WF-03）
  3. 実装順に、要件ごとに「設計（`/plan-spec`）→ 設計1つごとに実装（`/implement-tdd`）」を繰り返す

  開発開始の後に機能の追加・仕様の変更・機能の削除を行うときは、2 の代わりに変更要求（WF-20）から入る
- **WF-02** 複数の要件にまたがる設計（共通部品、非機能要件、入力の検証、エラー処理、出力形式）は、最初に着手する要件の設計に含める
- **WF-03** 要件定義の完了時に、要件の実装順を決める。他の要件の振る舞いに影響する要件（入力の検証、エラー処理、出力形式、非機能要件）は、影響を受ける要件より前に置く。順序と理由は要件定義の TASK の「完了したこと」に書く
- **WF-04** 各フェーズで既存のコードや資料の調査が必要になったら、組み込みの Explore サブエージェントに任せる（探索）

## フェーズの入力・出力・完了条件

| ID | フェーズ | 入力 | 出力 | 完了条件 |
|---|---|---|---|---|
| WF-05 | 開発開始 | テンプレート（overview.md、tech.md） | `docs/project/overview.md`、`docs/project/tech.md` | `（未記入）` が0件で、ユーザーが内容を承認した |
| WF-06 | 要件定義 | overview.md、tech.md | `docs/project/requirements/REQ-*.md` | plan-reviewer で合格（REV-06）し、ユーザーが要件一覧を承認した |
| WF-07 | 設計 | 対象の REQ | `docs/project/design/DES-*.md` | 対象 REQ の受け入れ基準がすべて DES に割り当てられ、plan-reviewer で合格し、ユーザーが承認した |
| WF-08 | 実装 | 対象の DES | テストコード、実装コード | TEST-01 の (1)〜(6) を終え、code-reviewer で合格した |

## タスク記録

- **WF-09** TASK の単位は GIT-03 の表の「TASK」列のとおりとし、1単位につき TASK ファイルを1つ作る。既存 DES の改訂（PLAN-22）は「1要件の設計」に、改訂した DES の実装は「1設計の実装」に含める
- **WF-10** 設計・実装を含む TASK の `related` には、扱う REQ と DES の ID を書く（`task.sh relate`）。DES の実装状況は、その DES を `related` に持つ TASK のうち番号が最も大きいものの `status` で判定する（該当 TASK がなければ未着手）。別の TASK から生まれた TASK（点検の結果の変更要求など）は、出所の TASK の ID も書いてよい。TASK の ID は WF-23〜25 の判定には使わない
- **WF-11** フェーズの切り替え時、質問への回答を得たとき（PLAN-08）、レビュー1ラウンドの終了時、セッションの終了・中断時に TASK ファイルを更新する（DOC-10〜13）

## 承認の依頼

- **WF-12** 人間への承認・確認の依頼（WF-05〜07、WF-18、WF-21、TEST-13、RF-42）は承認パケット（GIT-30）で行う。設計の承認は REQ ごと、実装の人間確認（TEST-13）は作業ブランチの範囲ごとに1回とする。PR のマージは承認を得てから Claude が行う（GIT-23）

## 戻り

- **WF-13** 実装中に設計の誤りや不足を見つけたら、実装を止めてユーザーに報告する。承認を得て DES を修正し、plan-reviewer のレビューをやり直してから実装に戻る
- **WF-14** 設計中に要件の誤りや不足を見つけたら、設計を止めてユーザーに報告する。承認を得て REQ を修正し、レビューをやり直す

## 人間の役割

- **WF-15** 人間が内容を書くのは開発開始（WF-05）のテンプレート記入までとする。以降、人間の作業は承認（WF-05〜07、WF-20 の変更要求の計画、WF-13・14 の戻り）と確認（TEST-13 の人間確認、REV-07・09 の残り・保留の判断、WF-18 の軽微な変更の完了時）に限る
- **WF-16** 要件定義・設計・軽微な変更では、Claude が推奨案で判断して進め、判断と理由を資料に残して承認時にまとめて示す（PLAN-05）。途中で人間に質問するのは PLAN-06 に当たる場合だけとする

## 軽微な変更

- **WF-17** 次をすべて満たす変更は、`/quick-change` の軽量フローで進めてよい。
  1. 新しい要件の追加や受け入れ基準の変更がない
  2. 公開インタフェース（DES のインタフェース欄に載るもの）の追加・変更がない
  3. 作成・変更するファイルが3つ以下
- **WF-18** 軽量フローでも、不具合の修正は再現テストで Red（TEST-03）を確かめて凍結（TEST-04）してから直し、code-reviewer を通す。振る舞いが DES の記述と変わったら DES と test-items.md も直す。資料だけの変更はテストを省き、plan-reviewer だけを通す。完了時に人間の確認を得る
- **WF-19** 軽量フローの途中で WF-17 の条件を1つでも満たさなくなったら、軽量フローを止め、変更要求（WF-20）に切り替える

## 変更要求

- **WF-20** 開発開始の後に、新しい要件の追加、既存 REQ の受け入れ基準の変更、機能の削除、architecture.md の変更のどれかを伴う変更は、変更要求として次の順で進める。
  1. 計画（`/plan-spec change <変更内容>`）: 影響一覧（PLAN-25）、overview.md の改訂（目的・スコープ・成功基準が変わる場合。PLAN-06 (1)）、REQ の追加・改訂・削除（PLAN-24）、変更分の実装順（WF-03 を準用）を作り、承認を得る（WF-21）
  2. 実装順に、影響を受ける REQ ごとに設計（既存 DES は PLAN-22 で改訂する）
  3. 設計1つごとに実装
- **WF-21** 変更要求の計画の完了条件は、影響一覧（PLAN-25）にある REQ・DES のそれぞれに「追加」「改訂」「削除」「影響なし（理由）」のどれかが書かれ、plan-reviewer で合格し、ユーザーが影響一覧・実装順・各 REQ の「判断」セクションを承認したこととする

## 進捗の報告

- **WF-22** 進捗の報告は、`docs/project/` の資料のフロントマター（`status`、`related`）と TASK の記述だけから作る。資料に根拠がない進捗や見込みは書かない。根拠がない項目は「記録なし」と書く
- **WF-23** 次の作業は、次のうち最初に当たるものとする。
  1. `in-progress` の TASK の「次の一手」
  2. `paused` の TASK の「次の一手」（再開してよいかユーザーに確認する）
  3. 開発開始が終わっていない（overview.md・tech.md が `final` でない）なら `/kickoff`
  4. REQ がなければ `/plan-spec`
  5. 実装順（WF-03、WF-20 の記録）で REQ を順に見て、最初に当たるもの: `final` の DES がない REQ は `/plan-spec REQ-xxx`、実装状況（WF-10）が `done` でない `final` の DES は `/implement-tdd DES-xxx`
  6. どれにも当たらなければ、全要件が完了している
- **WF-24** `status: draft` の REQ・DES で、それを `related` に持つ `in-progress`・`paused` の TASK がないものは、作業が止まっている資料として報告する

## プロジェクト全体の点検

- **WF-25** 前回の点検（題名が「リファクタリング」の `done` の TASK）より後に `done` になった実装の TASK（`related` に DES を持つ TASK）が5件以上あるとき、または全要件の実装が終わり（WF-23 (6)）その件数が1件以上あるときに、プロジェクト全体の点検（`/refactor`）の実行を1行で提案する。実行は人間の指示を待つ。提案は `/progress` の報告と `/implement-tdd` の完了時に行う
