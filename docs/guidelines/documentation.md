# ドキュメント運用ルール

docs 内の資料を作る・更新するときのルールの正本である。各ルールの ID は、レビューの指摘で参照する。

## 配置と構成

| ID | ルール |
|---|---|
| DOC-01 | 同じ情報は1か所にだけ書く。他の場所からはパスか ID で参照する（SSoT） |
| DOC-02 | 1ファイルには1つの責務だけを持たせる。2つ以上の目的を持つファイルは分割する |
| DOC-03 | 開発ルール（全プロジェクト共通）は `docs/guidelines/` に、プロジェクト固有の資料は `docs/project/` に置く |
| DOC-04 | ファイル名・フォルダ名は英語のケバブケースにする。ローマ字（例: `kanji-futan`）は使わない。用語集にある用語を名前に含めるときは、glossary.md の「コード上の名前」をケバブケースにして使う（例: `organizer_pays` → `organizer-pays`）。本文は日本語で書く |
| DOC-05 | 要件は `requirements/REQ-001-<名前>.md`、設計は `design/DES-001-<名前>.md`、ADR は `adr/ADR-0001-<名前>.md`、タスクは `tasks/TASK-001-<名前>.md` とし、1項目1ファイルにする。ID は欠番を再利用しない |
| DOC-06 | 設計は対応する要件を ID で参照する。要件の本文を設計に書き写さない |

## 作成と更新

| ID | ルール |
|---|---|
| DOC-07 | 新しい資料は `docs/guidelines/templates/` の同名テンプレートから作る |
| DOC-08 | 各資料の先頭に YAML フロントマターで `status`（`draft` / `final` / `retired`。タスクは `todo` / `in-progress` / `done` / `paused`）、`updated`（YYYY-MM-DD）、`related`（関連 ID の配列）を書く |
| DOC-09 | 固定の資料、フォルダ、オプション資料を追加・削除したら、`docs/README.md` の表を同じ変更で更新する |
| DOC-10 | 資料はその場で上書き更新する。版ごとのファイルや変更履歴欄は作らない。過去の内容は git 履歴で追う |
| DOC-11 | タスク記録の「作業ログ」セクションだけは追記のみとする（DOC-10 の例外）。新しい記録を下に足し、既存の記録は書き換えない |
| DOC-12 | 作業ログには、日付、フェーズ、行ったこと、結果（テスト件数、レビューの P0 / P1 / P2 件数など）、試して失敗したことを書く。コードの差分は書かず、コミットハッシュで参照する |
| DOC-13 | 作業ログは、フェーズの切り替え時、レビュー1ラウンドの終了時、セッションの終了・中断時に書く |
| DOC-21 | タスク記録の「次の一手」には、再開する Skill（引数を含む）と手順の番号、その手順で最初に行う1つの具体的な行動を書く（例: `/implement-tdd DES-003` の手順 10: 失敗している2件のテストを通す実装を書く）。Skill を使わない作業では行動だけを書く |
| DOC-14 | 不要になった資料は削除せず `status: retired` にする。ADR は DOC-16 の手順でのみ retired にする |

## ADR

| ID | ルール |
|---|---|
| DOC-15 | ADR は次の3条件をすべて満たす判断だけを記録する: (1) 後から変えるコストが高い (2) 文脈がないと意外に見える (3) 実際に複数の選択肢があり、理由を持って選んだ |
| DOC-16 | 確定（`final`）した ADR は書き換えない。判断を変えるときは新しい ADR を作り、古い ADR の `status` を `retired` にして `related` に新しい ADR の ID を足す（Superseded）。古い ADR で変更してよいのはフロントマターだけ |

## テンプレートの記入

| ID | ルール |
|---|---|
| DOC-17 | テンプレートの各見出しには `（未記入）` を置く。`（未記入）` が残っている見出しは空欄と判定する |
| DOC-18 | 「未定」「わからない」は有効な記入とする。その見出しの内容を各資料の「未決事項」に移す |

## 禁止事項

| ID | ルール |
|---|---|
| DOC-19 | 秘密情報（API キー、パスワード、トークン、個人情報）を資料に書かない |
| DOC-20 | 「適切に」「なるべく」「必要に応じて」など、判定できない表現を規則・基準・受け入れ基準に使わない。数値、条件、具体例で書く |
