# Git の運用

ブランチ、コミット、PR、承認の依頼、リリース、hotfix の基準の正本である。手順は各 Skill に、操作はスクリプト（`.claude/scripts/` の `task.sh begin`、`branch.sh`、`ci.sh`。開発用のリポジトリの作成は `create-repo.sh`、ハーネスの更新の取り込みは `update-harness.sh` で、人間は `npm run create-repo`・`npm run update-harness` で呼ぶ。使い方は各スクリプトの冒頭）にある。GitHub は `gh` CLI で操作する。

## ブランチ

- **GIT-01** 常設のブランチは `main`（リリース済みのコード。各マージコミットに版のタグを付ける）と `develop`（次のリリースに向けた統合先。GitHub の既定ブランチ）の2本とする
- **GIT-02** `main` と `develop` には直接コミット・プッシュ・マージしない。`develop` へは作業ブランチの PR で、`main` へは `develop` か `hotfix/` の PR で入れる（hook が止める）
- **GIT-03** 作業ブランチと TASK の単位は次の表のとおりとする。1本のブランチに複数の TASK が入る
- **GIT-04** 作業ブランチは `develop` の最新から切る（hotfix だけ `main` の最新のタグから）。`hotfix/` 以外の作業ブランチは同時に1本だけにする。変更のブランチ（`feature/change-`）で作業している間は、その範囲の設計・実装のためにブランチを切り替えない
- **GIT-05** マージした作業ブランチは削除する
- **GIT-06** マージ済みの作業ブランチと同じ名前のブランチは再利用しない（`branch.sh start` が止める）。中断した作業の再開のため、マージされていない同名のブランチは再利用する。日付を名前に使うブランチ（`feature/refactor-<YYYYMMDD>`）は、同じ名前のブランチ（ローカル・origin）があれば、`-2`・`-3` の連番を付けた名前にする

GIT-03 の表:

| 作業 | TASK（WF-09） | ブランチ名 | PR を完了させる時点 |
|---|---|---|---|
| 開発開始と要件定義 | 開発開始、要件定義で1つずつ | `feature/setup` | 要件定義の承認（WF-06） |
| 1要件の設計と、その全 DES の実装 | 設計で1つ、DES ごとに1つ | `feature/REQ-xxx-<REQ のファイル名の名前部分>` | その REQ の `final` の DES がすべて実装済み（WF-10 の `done`） |
| 変更要求（計画から全実装まで） | 計画で1つ、設計・実装は上の行と同じ | `feature/change-<TASK のファイル名>` | 変更要求の TASK の `related` にある REQ の `final` の DES がすべて `done` |
| 軽微な変更 | 1件で1つ | `feature/change-<TASK のファイル名>`（変更要求に切り替えたら同じブランチで続ける） | 完了時の確認（WF-18） |
| プロジェクト全体の点検 | 1回で1つ | `feature/refactor-<YYYYMMDD>`（同じ日の2回目からは `-2`・`-3`。GIT-06） | 完了時の確認 |
| 本番の緊急修正 | 1件で1つ | `hotfix/v<次のパッチ版>` | 完了時の確認（GIT-61） |
| ハーネス（このテンプレート）の更新の取り込み | 作らない | `feature/harness-update`（`npm run update-harness` が切る） | 取り込んだ差分の確認 |

## コミット

- **GIT-10** 次の時点でコミットする。TASK ファイルの変更は同じコミットに含める。
  1. TASK を作った直後
  2. 計画: 資料が plan-reviewer に合格したとき
  3. テストの凍結（TEST-04。テストファイルだけ）
  4. Green: テスト・リント・フォーマット・ビルドがすべて成功したとき
  5. Refactor の後と、レビューの終了（REV-06・07）の後
  6. ユーザーの承認・確認の後（`status: final`、TASK の `done`）
  7. セッションの中断・終了時
- **GIT-11** テストが失敗する状態のコードをコミットしない。例外は凍結コミット（Red）と、中断時のコミットだけとする
- **GIT-12** メッセージは `<type>(<ID>): <日本語の要約>` とし、本文の最後に `Refs: TASK-xxx` を書く。type は `feat`（機能の追加）、`fix`（不具合・指摘の修正）、`test`、`refactor`、`docs`（資料）、`chore`（TASK の記録、中断など）のどれか。ID は対象の DES・REQ・TASK。互換性を壊す変更は type の後に `!` を付ける（例: `feat(DES-003)!: …`）
- **GIT-13** 履歴を書き換えない（`git rebase`、`git commit --amend`、コミット済みの内容を消す `git reset`、強制プッシュ）。凍結コミットのハッシュ（TEST-04）を残すためである。`develop` の変更は `git merge develop` で取り込む

## プッシュ・PR・CI

- **GIT-20** プッシュは、承認・確認の依頼の直前、セッションの中断・終了時、PR のマージの直前に行う
- **GIT-21** 作業ブランチの最初のプッシュで、下書き PR を作る（向き先は `develop`、`hotfix/` は `main`）。本文は `.github/pull_request_template.md` の形にする。進捗は PR に書かない（正本は TASK。WF-22）
- **GIT-22** 作業ブランチの範囲（GIT-03 の表）の最後の承認・確認を依頼する前に、PR 本文を最新にして下書きを解除する
- **GIT-23** PR はマージコミットでマージする（squash と rebase は使わない）。マージは承認・確認を得てから行う
- **GIT-24** CI（`.github/workflows/ci.yml`）は、下書きでない PR と `main`・`develop` へのプッシュで、tech.md の開発コマンドを `ci.sh` で実行する。下書きでは動かさない（凍結コミットは意図的にテストが失敗するため）
- **GIT-25** 承認を依頼する前と PR をマージする直前に、CI の成功を確かめる。失敗したら同じブランチで直して、成功するまで繰り返す。CI が動かない（Actions が無効、`origin` がない）場合は、手元の `ci.sh` の結果で代える

## 承認・確認の依頼

- **GIT-30** 承認・確認の依頼（WF-12）は、次の形の「承認パケット」で行い、15行以内にする。差分の全文はチャットに出さない。
  1. 見出し: 何の承認か（ID と題名）
  2. 判断してほしいこと（はい / 直してほしい点 で答えられる形）
  3. 要点: 判断と理由（PLAN-05。最大5件）
  4. 重点確認箇所: 人が見るべき `パス:行` と理由（最大5件）
  5. 機械検証: テスト・リント・ビルドの結果（PR があれば CI の結果）と、レビューのラウンド数と P0 / P1 / P2 の件数
  6. 人間確認の項目（TEST-13。ない場合は省く）
  7. 差分リンク（GIT-31）
- **GIT-31** 差分リンクは、その承認の範囲だけを示す（`branch.sh link`）。実装（TEST-13）: テストは凍結コミットのページ、実装は凍結コミットから HEAD までの比較。それ以外: 作業の開始時に記録した起点のコミットから HEAD までの比較。範囲の最後の承認には PR のリンクも添える
- **GIT-32** 承認そのものはチャットで受ける。返答を受けたら PR へのコメント（`gh pr view --comments` と行へのコメント）も読み、指摘として扱う
- **GIT-33** リモート `origin` がない場合は、PR の代わりに承認後に手元で `develop` へ `--no-ff` でマージし（GIT-02 の例外。hook も `origin` がないときだけ通す）、差分リンクの代わりに `git diff --stat` を示す。スクリプトはこの場合を自動で扱う

## リリースと hotfix

- **GIT-50** リリースは、全要件の実装が終わったとき（WF-23 (6)）、またはユーザーが指示したときに行う（`/release`）
- **GIT-51** 版番号は SemVer（`vX.Y.Z`）とする。初回は `v1.0.0`。2回目以降は、前回のタグ以降のコミットに `!` があればメジャー、`feat` があればマイナー、それ以外はパッチを上げる（GIT-12）
- **GIT-52** リリースは `develop` → `main` の PR をマージコミットで入れ（`develop` は残す）、`main` のマージコミットに注釈付きの版のタグとリリースノートを付ける
- **GIT-60** hotfix は、リリース済みの `main` に緊急の修正が必要で、`develop` に未リリースの変更があるときだけ使う。それ以外は通常の軽微な変更か変更要求で直す
- **GIT-61** hotfix は、軽微な変更の基準（WF-17〜19）で直し、`main` 向きの PR でマージしてタグとリリースノートを付けた後、同じブランチから `develop` 向きの PR でも入れる（`/quick-change hotfix`）
