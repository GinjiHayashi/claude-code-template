# Git の運用

ブランチ、コミット、プッシュ、PR、CI、承認の依頼、リリース、hotfix の正本である。ブランチの作成・PR・差分リンクは `.claude/scripts/branch.sh`、CI の確認は `.claude/scripts/ci.sh`（使い方はスクリプト冒頭）で行う。GitHub は `gh` CLI で操作する。

## ブランチ

| ID | ルール |
|---|---|
| GIT-01 | 常設のブランチは `main`（リリース済みのコード。各マージコミットに版のタグを付ける）と `develop`（次のリリースに向けた統合先）の2本とする。GitHub の既定ブランチは `develop` にする |
| GIT-02 | `main` と `develop` には直接コミット・プッシュ・マージしない。`develop` へは作業ブランチの PR で、`main` へは `develop` か `hotfix/` の PR で入れる（hook が止める） |
| GIT-03 | 作業ブランチの単位と名前は次の表のとおりとする。TASK の単位（WF-08）は変えず、1本のブランチに複数の TASK が入る |
| GIT-04 | 作業ブランチは `bash .claude/scripts/branch.sh start <ブランチ名>` で作る（`develop` の最新から切る。既にあれば切り替える）。`hotfix/` 以外の作業ブランチは同時に1本だけにする。変更のブランチ（`feature/change-`）で作業している間は、その範囲の設計・実装のためにブランチを切り替えない |
| GIT-05 | マージした作業ブランチは削除する |

GIT-03 の表:

| 作業 | ブランチ名 | 範囲（PR を完了させる時点） |
|---|---|---|
| 開発開始と要件定義 | `feature/setup` | 要件定義の承認（WF-05） |
| 1要件の設計と、その全 DES の実装 | `feature/REQ-xxx-<REQ のファイル名の名前部分>` | その REQ の `final` の DES の実装状況（WF-20）がすべて `done` になったとき |
| 変更要求（計画から全実装まで） | `feature/change-<task.sh new に渡したファイル名>` | 変更要求の TASK の `related` にある REQ の `final` の DES がすべて `done` になったとき |
| 軽微な変更 | `feature/change-<task.sh new に渡したファイル名>`（変更要求に切り替えたら、同じブランチで続ける） | 完了時の確認（WF-15） |
| プロジェクト全体の点検 | `feature/refactor-<YYYYMMDD>` | 完了時の確認 |
| 本番の緊急修正 | `hotfix/v<次のパッチ版>`（`branch.sh start hotfix` が決める） | 完了時の確認（GIT-61） |

## コミット

| ID | ルール |
|---|---|
| GIT-10 | 次の時点でコミットする。(1) TASK を作った直後 (2) 計画: 資料が plan-reviewer に合格したとき (3) テストの凍結（TEST-04。テストファイルだけ） (4) Green: テスト・リント・フォーマット・ビルドがすべて成功したとき (5) Refactor の後と、レビューの合格（REV-06）またはラウンド上限（REV-07）の後 (6) ユーザーの承認・確認の後（`status: final`、TASK の `done`） (7) セッションの中断・終了時。TASK ファイルの変更は同じコミットに含める |
| GIT-11 | テストが失敗する状態のコードをコミットしない。例外は凍結コミット（Red）と、中断時のコミットだけとする |
| GIT-12 | メッセージは `<type>(<ID>): <日本語の要約>` とし、本文の最後に `Refs: TASK-xxx` を書く。type は `feat`（機能の追加）、`fix`（不具合・指摘の修正）、`test`、`refactor`、`docs`（資料）、`chore`（TASK の記録、中断など）のどれか。ID は対象の DES・REQ・TASK。互換性を壊す変更は type の後に `!` を付ける（例: `feat(DES-003)!: …`） |
| GIT-13 | 履歴を書き換えない。`git rebase`、`git commit --amend`、コミット済みの内容を消す `git reset`、強制プッシュをしない。凍結コミットのハッシュ（TEST-04）を残すためである。`develop` の変更を取り込むときは `git merge develop` を使う |

## プッシュと PR

| ID | ルール |
|---|---|
| GIT-20 | プッシュは、承認・確認の依頼の直前、セッションの中断・終了時、PR のマージの直前に行う |
| GIT-21 | 作業ブランチの最初のプッシュで、下書き PR を作る（`branch.sh pr`。向き先は `develop`、`hotfix/` は `main`）。本文は `.github/pull_request_template.md` の形にする。進捗は PR に書かない（正本は TASK。WF-21） |
| GIT-22 | 作業ブランチの範囲（GIT-03 の表）の最後の承認・確認を依頼する前に、PR 本文を最新にして下書きを解除する（`gh pr ready`） |
| GIT-23 | 承認・確認を得たら、GIT-10 (6) のコミットとプッシュをしてから `gh pr merge --merge --delete-branch` で PR をマージする（マージコミット。squash と rebase は使わない）。その後 `git switch develop && git pull --ff-only` で手元を最新にする |

## CI

| ID | ルール |
|---|---|
| GIT-24 | CI は `.github/workflows/ci.yml` で、下書きでない PR（作成、プッシュ、再オープン、下書きの解除）と、`main`・`develop` へのプッシュのときに `bash .claude/scripts/ci.sh` を実行する。下書きの PR では動かさない（凍結コミットは意図的にテストが失敗するため。TEST-04）。ci.sh は tech.md の開発コマンドを、依存関係のインストール、フォーマット（整形で差分が出たら失敗）、リント、ビルド、テスト（全件）の順に実行する。tech.md が `final` でなければ全体を飛ばし、`final` の後は「なし」の操作だけを飛ばして、未記入の操作は失敗とする。言語の実行環境の準備は、ci.yml の「言語の実行環境の準備」の印の間に `/kickoff` で書く |
| GIT-25 | 下書きを解除したら（GIT-22）、承認を依頼する前に `gh pr checks <PR 番号> --watch` で CI の結果を待ち、承認パケットの機械検証（GIT-30 (5)）に書く。PR をマージする直前（GIT-23、GIT-52、GIT-61）にも同じコマンドで CI の成功を確かめる。失敗したら同じブランチで直してコミット・プッシュし、成功するまで繰り返す。チェックが報告されない（Actions が無効）場合と、`origin` がない場合（GIT-33）は、手元で ci.sh を実行して代わりにする |

## 承認・確認の依頼

| ID | ルール |
|---|---|
| GIT-30 | 承認・確認の依頼（WF-04〜06、WF-15、WF-19、TEST-10、RF-42）は、次の形の「承認パケット」で行い、15行以内にする。差分の全文はチャットに出さない。(1) 見出し: 何の承認か（ID と題名） (2) 判断してほしいこと（はい / 直してほしい点 で答えられる形） (3) 要点: 判断と理由（PLAN-18。最大5件） (4) 重点確認箇所: 人が見るべき `パス:行` と理由（最大5件） (5) 機械検証: テスト・リント・ビルドの結果（PR があれば CI の結果。GIT-25）と、レビューのラウンド数と P0 / P1 / P2 の件数 (6) 人間確認の項目（TEST-10。ない場合は省く） (7) 差分リンク（GIT-31） |
| GIT-31 | 差分リンクは、その承認の範囲だけを示す。`bash .claude/scripts/branch.sh link <起点のコミット>` で作る。実装（TEST-10）: テストは凍結コミットのページ、実装は凍結コミットから HEAD までの比較。資料（WF-04〜06、WF-19）と軽微な変更・全体点検: 作業の開始時に記録したコミットから HEAD までの比較。範囲の最後の承認には PR のリンクも添える |
| GIT-32 | 承認そのものはチャットで受ける。返答を受けたら、`gh pr view --comments` と `gh api repos/{owner}/{repo}/pulls/<PR 番号>/comments` で PR へのコメントを読み、指摘として扱う |
| GIT-33 | リモート `origin` がない場合は、PR の作成とマージ（GIT-21〜23）の代わりに、承認後に `git switch develop && git merge --no-ff <作業ブランチ>` でマージする（GIT-02 の例外。hook も `origin` がないときだけ通す）。差分リンクの代わりに `git diff --stat <起点>..HEAD` の結果を載せる（`branch.sh link` が出す） |

## リリース

| ID | ルール |
|---|---|
| GIT-50 | リリースは、全要件の実装が終わったとき（WF-22 (6)）、またはユーザーが指示したときに、`/release` で行う |
| GIT-51 | 版番号は SemVer（`vX.Y.Z`）とする。初回は `v1.0.0`。2回目以降は、前回のタグ以降のコミットに `!` があればメジャー、`feat` があればマイナー、それ以外はパッチを上げる（GIT-12） |
| GIT-52 | 手順は次のとおりとする。(1) `develop` → `main` の PR を作る。本文に版番号と、前回のタグ以降にマージした作業ブランチの一覧を書く (2) 承認パケット（GIT-30）で承認を求める (3) `gh pr merge --merge` でマージする（`develop` は削除しない） (4) `main` のマージコミットに注釈付きタグを付けてプッシュする (5) `gh release create <版> --generate-notes` でリリースノートを作る |

## hotfix

| ID | ルール |
|---|---|
| GIT-60 | hotfix は、リリース済みの `main` に緊急の修正が必要で、`develop` に未リリースの変更があるときだけ使う。それ以外は通常の軽微な変更か変更要求で直す |
| GIT-61 | 手順は `/quick-change hotfix <変更内容>` で行う。`branch.sh start hotfix` で最新のタグから `hotfix/v<次のパッチ版>` を切り、軽微な変更の手順（WF-15）で直す。確認を得たら (1) `main` 向きの PR を `gh pr merge --merge`（ブランチは残す）でマージし、GIT-52 の (4)(5) でタグとリリースノートを作る (2) 同じブランチから `develop` 向きの PR を作ってマージする。コンフリクトしたら hotfix ブランチに `git merge develop` で取り込んで解消し、テスト・リント・ビルドを成功させてからマージする (3) ブランチを削除する |
