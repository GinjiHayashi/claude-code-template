# Claude Code 開発環境テンプレート

## 1. 概要

Claude Code で開発を進めるための、言語に依存しない（Python や SQL などに依存しない）共通の開発環境です。

- 開発は **探索 → 計画 → 実装 → レビュー** を1サイクルとし、これを繰り返します。
- 実装はテスト駆動開発（TDD）で進めます。計画の完了後、実装より先にテストを書きます。
- レビューは文脈を引き継がないサブエージェントが行います。指摘は観点ごとに P0 / P1 / P2 に分類し、終了条件を定量的に決めます。
- ルールの正本は `docs/guidelines/` に置き、`.claude/` 側（Skills・agents）はそれを参照するだけにします（SSoT）。

## 2. クイックスタート

やりたいことに合わせて、次の表から入口を選びます。各手順の詳細は「4. 開発の進め方」と、各 Skill（`.claude/skills/`）が正本です。

| やりたいこと | 入口 | 詳細 |
|---|---|---|
| 新しいプロジェクトを始める | `/kickoff` | 2.2 |
| 機能を追加する・仕様を変える・機能を削除する | `/plan-spec change <変更内容>` | 2.3 |
| 小さな不具合や文言・設定を直す | `/quick-change <変更内容>` | 2.4 |
| ドキュメントだけを直す | `/quick-change <変更内容>` | 2.5 |
| 中断した作業を再開する | `claude` を起動するだけ | 2.6 |
| 進捗・次の作業・残作業を確かめる | `/progress` | 2.7 |
| コード全体を整理し、資料どうしの齟齬を直す | `/refactor` | 2.8 |
| リリースする（develop を main に入れる） | `/release` | 2.9 |
| リリース済みの本番の不具合を急いで直す | `/quick-change hotfix <変更内容>` | 2.10 |

小さな変更かどうか迷ったら `/quick-change` から始めて構いません。条件（2.4）を満たさないと分かった時点で、Claude が変更要求に切り替えます（WF-16）。

### 2.1 共通の準備

1. このテンプレートの中身を、開発するリポジトリの直下にコピーします（`.claude/`、`docs/`、`CLAUDE.md`、`.mcp.json`、`.gitignore`）。既存のリポジトリに入れる場合は、同名のファイルを上書きしないよう注意します。
2. git リポジトリにし、`main` と `develop` を用意します（4.12）。テストの凍結、レビューの差分、承認用の差分リンクは git のコミットを使います。Claude は `main` と `develop` に直接コミットできない（hook が止める）ため、最初のコミットだけは人間が行います。
   ```bash
   git init -b main
   git add -A && git commit -m "chore: テンプレートを導入"
   git switch -c develop
   ```
3. GitHub を使う場合は、`gh` CLI を用意してリポジトリを作り、両方のブランチをプッシュして、既定ブランチを `develop` にします。リポジトリの設定で、マージ方式を「Create a merge commit」だけにし、マージ後のブランチの自動削除を有効にします。ルールセットが使えるプラン（公開リポジトリ、または Pro / Team 以上）なら、`main` と `develop` に「PR を必須」「強制プッシュの禁止」「削除の禁止」を設定し、CI を一度動かした後で、必須のステータスチェックに `ci` を加えます。CI（`.github/workflows/ci.yml`）は Actions が有効なら追加の設定なしで動きます（4.12）。
   ```bash
   gh repo create <名前> --private --source . --remote origin
   git push -u origin main develop
   gh repo edit --default-branch develop --enable-merge-commit --enable-squash-merge=false --enable-rebase-merge=false --delete-branch-on-merge
   ```
4. bash が使えることを確認します（Windows では Git Bash か WSL）。hooks と `.claude/scripts/` に必要です。
5. `claude` を**リポジトリの直下で**、`develop` にいる状態で起動します。サブディレクトリで起動すると hooks が動きません（4.10）。初回は Context7（MCP サーバー）の使用を承認します。

### 2.2 新しいプロジェクトを始める

```text
/kickoff → /plan-spec → （要件ごとに）/plan-spec REQ-xxx → （設計ごとに）/implement-tdd DES-xxx
```

1. `/kickoff` を実行します。`docs/project/` に「概要」（overview.md）と「技術・環境」（tech.md）のテンプレートがコピーされます。
2. 各見出しの `（未記入）` を自分の言葉で書き換えます。全部埋めなくても構いません。残った空欄は Claude が1問ずつ質問して埋めます。技術・環境の「開発コマンド」（テスト、リント、フォーマット、ビルド）は必ず決めます。
3. Claude が示す内容（用語集の英語名を含む）を**承認**します。
4. `/plan-spec` を実行します。Claude が要件（REQ）と実装順を決め、AI レビューを通します。要件一覧・実装順・各 REQ の「判断」を**承認**します。
5. 実装順に `/plan-spec REQ-001` などで要件ごとに設計（DES）とテスト項目を作ります。設計と各 DES の「判断」を**承認**します。
6. `/implement-tdd DES-001` などで設計1つずつ実装します。テストの作成 → Red の確認 → テストのレビュー → テストの凍結 → 実装 → 整理 → コードのレビューまでを Claude が進めます。最後に示される人間確認の項目を**確認**します。
7. 全要件が終わるまで 5〜6 を繰り返します。

### 2.3 機能を追加する・仕様を変える・機能を削除する

開発開始の後に、新しい要件の追加、既存の受け入れ基準の変更、機能の削除、構成（architecture.md）の変更のどれかを伴う場合の手順です（WF-18）。

```text
/plan-spec change <変更内容> → （影響する要件ごとに）/plan-spec REQ-xxx → （設計ごとに）/implement-tdd DES-xxx
```

1. `/plan-spec change <変更内容>` を実行します（例: `/plan-spec change 割り勘の端数を切り上げではなく指定した人が負担できるようにする`）。
2. Claude が影響一覧（変える REQ・DES・テスト・資料）を作り、REQ を追加・改訂・削除して実装順を決めます。目的やスコープが変わる場合だけ、overview.md の改訂点を質問されます。
3. 影響一覧・実装順・各 REQ の「判断」を**承認**します。
4. 実装順に `/plan-spec REQ-xxx` で設計し、**承認**します。既存の振る舞いを変える場合は、新しい DES を足さずに既存の DES が改訂されます。
5. `/implement-tdd DES-xxx` で実装し、人間確認の項目を**確認**します。

変える要件も設計も1つだけの場合は、1から5までを1つのタスク記録で続けて進められます（WF-08）。

### 2.4 小さな不具合や文言・設定を直す

次をすべて満たす変更が対象です（WF-14）。1つでも外れる場合は 2.3 の手順を使います。

- 新しい要件の追加や受け入れ基準の変更がない
- 公開インタフェース（DES のインタフェース欄に載るもの）の追加・変更がない
- 作成・変更するファイルが3つ以下

```text
/quick-change <変更内容>
```

1. `/quick-change <変更内容>` を実行します（例: `/quick-change 合計が0円のときにエラーになる不具合を直す`）。
2. Claude が探索して上の3条件を判定します。不具合なら再現テストを書いて失敗を確認し、テストを凍結してから修正します。テスト・リント・ビルドとコードのレビューまでを Claude が進めます。
3. 最後に示される変更内容・レビュー結果・人間確認の点を**確認**します。

### 2.5 ドキュメントだけを直す

ドキュメント専用の Skill はなく、`/quick-change` の「資料だけの変更」の手順を使います（WF-15）。テストは省き、計画書の AI レビュー（plan-reviewer）だけを通します。

```text
/quick-change <変更内容>
```

直す資料によって、入口が変わります。

| 直す内容 | 入口 |
|---|---|
| 誤字、表現、説明の補足など、意味を変えない修正（REQ・DES・architecture.md・用語集・tech.md など） | `/quick-change` |
| REQ の受け入れ基準の変更、要件の追加・削除、overview.md の目的・スコープ・成功基準の変更、architecture.md の構成の変更 | `/plan-spec change`（2.3） |
| DES の公開インタフェース（インタフェース欄）の変更 | `/plan-spec change`（2.3。WF-14 の (2) から外れるため） |

`docs/guidelines/`（全プロジェクト共通のルール）を直す場合も `/quick-change` を推奨します。ただし、これは手順として定められたものではなく推測による推奨です。ルールは Skills・agents から ID で参照されているため、ルール ID を変更・削除した場合は `.claude/` と `docs/` を ID で検索して参照切れがないことを確かめてください。資料を追加・削除した場合は `docs/README.md` の表も同じ変更で更新します（DOC-09）。

### 2.6 中断した作業を再開する

`claude` をリポジトリの直下で起動すると、session-start hook が進行中・中断中のタスク記録（`docs/project/tasks/`）の「現在のフェーズ」と「次の一手」を Claude に渡します。「続きをやって」と頼めば、その位置から再開します。「次の一手」には再開する Skill と手順の番号が書かれ（DOC-21）、質問の途中だった場合は回答済みの質問が記録されているので、未回答の質問から再開します（PLAN-27）。

### 2.7 進捗・次の作業・残作業を確かめる

```text
/progress
```

「今どこまで進んだ？」と聞くだけでも使われます。Claude が `.claude/scripts/progress.sh` で要件・設計・タスク記録の状態を集計し、次の5項目を報告します。ファイルは変更しません。

| 項目 | 内容 |
|---|---|
| 現在地 | 開発のどの段階か。要件と設計の完了数 |
| 次の作業 | 次に実行する Skill とその引数（決め方は WF-22） |
| 進行中 | 進行中・中断中のタスクの現在のフェーズと次の一手 |
| 残作業 | 実装順に、要件ごとの設計・実装の残り |
| 人間の対応待ち | 承認待ちの要件・設計、保留中の指摘などの未解決事項、止まっている資料 |

作業の途中で `/progress` を挟んでも、記録は変わりません。報告の後に「続けて」と言えば、進行中のタスクの「次の一手」から再開します。報告は資料とタスク記録だけを根拠にします（WF-21）。記録にない進捗は「記録なし」と表示されるため、タスク記録の更新（WF-09）が報告の正確さを決めます。

### 2.8 コード全体を整理し、資料どうしの齟齬を直す

```text
/refactor [点検するディレクトリ]
```

差分のレビューでは見えない、実装や変更を重ねるうちに積み重なる問題を、リポジトリ全体から探して直します。ファイルをまたぐ重複、少しずつの肥大、名前の揺れ、設計とコードのずれ、ID の参照切れなどが対象です。観点の一覧（コード RF-10〜19、資料 RF-20〜31）は [`docs/guidelines/refactoring.md`](docs/guidelines/refactoring.md) が正本です。

1. `/refactor` を実行します。Claude がテスト・リント・ビルドを実行し、機械で判定できる観点を `.claude/scripts/audit.sh` で、意味の判断が要る観点を code-auditor と docs-auditor（サブエージェント）で調べます。
2. 指摘は「自動修正」「変更要求の候補」「任意（P2）」に分類されます。診断結果と修正計画を**承認**し、任意の指摘から直すものを選びます。
3. Claude が振る舞いを変えない修正だけを直します。全テストが成功したままでテストファイルは変えず、1件ごとにテストを実行し、最後に AI レビューを通します。
4. 直した内容と変更要求の候補を**確認**します。仕様に関わる候補は `/plan-spec change`（2.3）で1件ずつ進めます。

実行するのは人間の指示があったときだけです。全要件の実装が終わったとき、変更要求の実装が終わったとき、前回の点検の後に実装のタスクが5件終わったときに、Claude が実行を提案します（WF-24）。

### 2.9 リリースする

```text
/release [版番号]
```

全要件の実装が終わったとき（または任意の時点で指示したとき）に、`develop` の内容を `main` に入れます（GIT-50〜52）。

1. `/release` を実行します。Claude が、進行中のタスクや未マージの作業ブランチがないこと、テスト・リント・ビルドが通ることを確かめます。
2. Claude が版番号を決めます。初回は `v1.0.0`、2回目以降はコミットの種類（GIT-12）から、互換性を壊す変更があればメジャー、機能の追加があればマイナー、それ以外はパッチを上げます。
3. `develop` → `main` の PR と承認パケットが示されるので、**承認**します。
4. Claude がマージし、タグを付けてリリースノートを作ります。

### 2.10 リリース済みの本番の不具合を急いで直す（hotfix）

```text
/quick-change hotfix <変更内容>
```

リリース済みの `main` に緊急の修正が必要で、`develop` に未リリースの変更がある場合だけ使います（GIT-60）。それ以外は 2.4 の通常の手順で直します。

1. Claude が最新のタグから `hotfix/v<次のパッチ版>` を作り、2.4 と同じ手順（再現テスト → 凍結 → 修正 → レビュー）で直します。
2. 承認パケットで**確認**します。
3. Claude が `main` にマージしてタグとリリースノートを作り、同じ修正を `develop` にも入れます（GIT-61）。

## 3. フォルダ・ファイル構成

本 README は、リポジトリ全体の地図と開発の進め方の正本です。docs 内の資料の一覧は [`docs/README.md`](docs/README.md) を正本にします。

```text
.
├── README.md                  # 本ファイル。環境の概要、構成、開発の進め方
├── CLAUDE.md                  # Claude が毎セッション読む指示。落とし穴と参照先ポインタのみ
├── .mcp.json                  # 共有する MCP サーバー。Context7（ライブラリの最新ドキュメント）のみ
├── .gitignore                 # レビュー用の差分ファイル（.claude/review/）を除外
├── .github/
│   ├── pull_request_template.md  # PR 本文の形（GIT-21）
│   └── workflows/ci.yml       # CI。下書きでない PR と main・develop へのプッシュで ci.sh を実行（GIT-24）
├── .claude/
│   ├── settings.json          # 権限、hooks、応答言語（日本語）などの共有設定
│   ├── hooks/                 # hook のスクリプト。session-start / freeze-guard / branch-guard / format と共通関数 lib.sh
│   ├── scripts/               # task.sh（タスク記録の作成・更新）、branch.sh（作業ブランチ・下書き PR・差分リンク）、ci.sh（開発コマンドを順に実行する CI の確認）、progress.sh（進捗の集計）、audit.sh（全体点検の機械判定）。後の2つは読み取りのみ
│   ├── agents/                # サブエージェント定義。plan-reviewer / test-reviewer / code-reviewer、全体点検の code-auditor / docs-auditor（探索は組み込みの Explore）
│   └── skills/                # 各フェーズの手順。/kickoff /plan-spec /implement-tdd /review-loop /quick-change /progress /refactor /release
└── docs/
    ├── README.md              # docs 内の固定資料とフォルダの索引。「いつ読むか」の対応表
    ├── guidelines/            # 開発ルール。全プロジェクト共通
    │   ├── workflow.md        # ワークフロー
    │   ├── planning.md        # 計画
    │   ├── testing.md         # テスト
    │   ├── review.md          # レビュー
    │   ├── documentation.md   # ドキュメント運用
    │   ├── coding.md          # コーディング原則
    │   ├── refactoring.md     # プロジェクト全体の点検（リファクタリング）
    │   ├── git.md             # ブランチ、コミット、PR、承認パケット、リリース、hotfix
    │   └── templates/         # 各資料のテンプレート（project/ の資料と同名。フォルダ内の資料は単数形: requirement.md など）
    └── project/               # このプロジェクト固有の資料
        ├── overview.md        # 概要（開発開始時に人間が記入）
        ├── tech.md            # 技術・環境（開発開始時に人間が記入）
        ├── architecture.md    # アーキテクチャ・構造
        ├── glossary.md        # 用語集（用語とコード上の英語名）
        ├── test-items.md      # 全設計のテスト項目（設計ごとの見出し）
        ├── requirements/      # 要件。REQ-001-<名前>.md の1項目1ファイル
        ├── design/            # 設計。DES-001-<名前>.md の1項目1ファイル
        ├── adr/               # ADR。ADR-0001-<名前>.md の1判断1ファイル
        └── tasks/             # タスク記録。TASK-001-<名前>.md の1タスク1ファイル
```


### 3.1 `docs/guidelines/`（全プロジェクト共通の開発ルール）

| 資料 | 書く内容 |
|---|---|
| ワークフロー | 探索→計画→実装→レビューのループ。各フェーズの入力・出力・完了条件 |
| 計画 | 2階層の計画（要件 / 設計）の書き方、設計に必ず書く項目、質問の進め方（1問ずつ）、ADR を書く条件 |
| テスト | TDD の手順、Red の確認、テスト項目の3分類（機械検証 / AI レビュー / 人間確認）、禁止事項、必須ケース（異常系・境界値・敵対的入力） |
| レビュー | 判定可能な粒度の観点、P0 / P1 / P2 の定義、終了条件 |
| ドキュメント運用 | SSoT、1ファイル1責務、更新方式、メタ情報、索引の更新ルール |
| コーディング原則 | 言語に依存しない設計原則（判定可能なものに限る） |
| リファクタリング | プロジェクト全体の点検の観点（コードの横断的な問題、資料どうし・資料とコードの齟齬）、修正の分類（自動修正 / 変更要求の候補 / 任意） |
| Git の運用 | ブランチの種類と単位、コミットの時点とメッセージ、プッシュと PR、承認パケット、リリース、hotfix |
| `templates/` | 各資料のテンプレート（要件テンプレートを含む） |

ファイル名は英語のケバブケースにします。

### 3.2 `docs/project/`（プロジェクト固有の資料）

最初から作る**コア資料**です。

| 資料 | 書く内容 | 書かないこと |
|---|---|---|
| 概要 | 目的、対象ユーザー、スコープ・非スコープ、成功基準など。**開発開始時に人間が記入するテンプレートを兼ねる** | 技術選定、実装方法 |
| 要件（REQ-xxx） | 機能要件・非機能要件と、それぞれの受け入れ基準 | 実装単位の設計 |
| 設計（DES-xxx） | 要件を実装単位に分けた実装レベルの設計。ファイルパス、インタフェース（入力・出力・エラー）、データ構造、処理方針（既存の振る舞いへの影響を含む）、対応する要件 ID | 要件の再記述、コード本体、テスト項目（テスト項目表に書く） |
| テスト項目表 | 全設計のテスト項目を1ファイルにまとめる。設計ごとの見出しの下に、機械検証 / AI レビュー / 人間確認の表を置く | 設計の内容 |
| アーキテクチャ・構造 | 構成要素と境界、依存の向き、ディレクトリ構成、命名規則 | 個々の機能の仕様 |
| 技術・環境 | **開発開始時に人間が記入するテンプレートを兼ねる**。言語、技術スタック、制約、開発コマンド（test / lint / format / build）とリンター・フォーマッターの正本 | 選定理由（ADR に書く） |
| ADR | 1判断1ファイル。背景、選択肢、決定、結果 | 現状の仕様 |
| 用語集 | プロジェクト固有の用語、定義、コード上の名前（英語）。開発開始時に決め、ファイル名やコードの名前はこれを使う | 実装の詳細 |
| タスク記録 | 進行中タスクの現在地、完了したこと、次の一手、未解決事項。作成と定型の更新は `.claude/scripts/task.sh` で行う | 設計内容 |

次の**オプション資料**は、必要になった時点で追加します。

| 資料 | 追加するきっかけ |
|---|---|
| リスク・技術的負債 | 既知の問題を意図的に後回しにすると決めたとき |
| 調査メモ | ADR の根拠になる調査が長くなったとき |
| データモデル・API 契約 | 永続データや外部インタフェースを持つとき |
| 実行時・配置のビュー | 複数プロセスやインフラ構成を持つとき |
| 運用手順 | デプロイなど、人が繰り返す手順が生まれたとき |

ファイル名は英語のケバブケースにします。要件と設計は種類別のフォルダに1項目1ファイルで置き、設計は対応する要件を ID で参照します。

## 4. 開発の進め方

### 4.1 開発開始（要件定義）

1. `/kickoff` を起動すると、「概要」と「技術・環境」の2つのテンプレートが `docs/project/` にコピーされます。技術・環境では、言語、リンター、フォーマッター、テストツール、開発コマンドを決めます。
2. テンプレートには見出しと「何を書くか」の説明だけが書かれています。各見出しの下にある `（未記入）` を、自分の言葉で書き換えます。全部を埋めなくても構いません。
3. Claude が見出しごとに判定します。
   - `（未記入）` が残っている見出しは、Claude が1問ずつ質問して埋めます。最初に、全部で何問あり、それぞれ何を聞くかの一覧が示されます（PLAN-26）。
   - 記入済みの見出しは、不足、考慮漏れ、矛盾の指摘と議論だけを行います。
   - 空欄を先にすべて埋めてから、見出しをまたいだ全体の議論に入ります。
4. 「未定」「わからない」も有効な回答です。未決事項として記録し、後の工程で回収します。
5. 議論で決まった判断のうち ADR の条件を満たすものは ADR に、用語は用語集に記録します。用語には、ファイル名やコードで使う英語名（ローマ字は使わない）もこの時点で決めます。

### 4.2 開発サイクル

全体の流れは、概要（人間が記入）→ 要件 → 設計 → テスト → 実装 → レビューです。

| フェーズ | 内容 | 担当 |
|---|---|---|
| 探索 | 既存コードと資料の調査 | 組み込みの Explore サブエージェント |
| 計画 | 要件（REQ）と実装順 → 設計（DES）とテスト項目表。Claude が推奨案で決め、判断は REQ・DES の「判断」セクションに残す（PLAN-18）。質問は PLAN-19 の場合だけ。ADR は DOC-15 を満たす判断だけ書く。計画書は AI がレビューする | Skill + レビュー用サブエージェント |
| 実装 | 設計（DES）1つ単位で進める。テストとスタブを書く → 全テストの失敗を確認（Red）→ AI がテストの妥当性をレビュー → テストを凍結 → 実装（Green）→ 整理（Refactor）。正本は `docs/guidelines/testing.md` | Skill + テストレビュー用サブエージェント |
| レビュー | 差分をファイルに保存して渡し、観点ごとに P0 / P1 / P2 で出力する。計画書とテストコードもレビュー対象 | レビュー用サブエージェント |

レビューの終了条件の要点は次のとおりです。正本は [`docs/guidelines/review.md`](docs/guidelines/review.md) です。

- **合格**: P0 と P1（保留中を除く）がゼロになったら終了します。P2（改善提案）は修正しなくて構いません。
- **ラウンド上限**: 3ラウンドで終了し、残った指摘は人間が判断します。
- **保留**: 要件・設計の変更が必要な P1、ルール同士が矛盾する P1、指摘が振動した P1 は、人間判定待ちとして保留できます。
- **退行**: 既存のテストや受け入れ基準で動いていた入力が動かなくなる指摘は、P0 です。
- **合格後の変更**: 合格・上限到達の後は対象を変えず、残した P2 はタスク記録に書きます。変えた場合は、その差分だけを確認ラウンドでレビューします。

### 4.3 人間の役割

人間が内容を書くのは、開発開始のテンプレート記入までです。それ以降の作業は承認と確認だけです（正本は `docs/guidelines/workflow.md` の WF-12・13）。

| 人間の作業 | タイミング |
|---|---|
| 承認 | 開発開始の完了時、要件一覧の完了時、変更要求の計画の完了時、各要件の設計の完了時、要件・設計を戻すとき、リリースの前 |
| 確認 | 設計の人間確認の項目、レビューで残った指摘・保留した指摘、軽微な変更の完了時 |
| PR のマージの許可 | 作業ブランチの範囲の最後の承認・確認の後に、Claude が `gh pr merge` を実行するときの確認プロンプト |

承認と確認の依頼は「承認パケット」で示されます（GIT-30）。15行以内の要約（判断してほしいこと、要点、重点確認箇所、検証結果、人間確認の項目）と、その承認の範囲だけの GitHub の差分リンク（テストと実装は別のリンク）です。差分の行に GitHub でコメントすると、Claude が返答の後に読んで指摘として扱います。承認そのものはチャットで答えます。

要件と設計の判断は Claude が推奨案で決め、各 REQ・DES の「判断」セクションに選択肢と理由を残します。途中で質問するのは、目的や受け入れ基準が変わる判断、後から戻せない判断、資料どうしの矛盾に限ります（PLAN-18・19）。

### 4.4 軽微な変更

次をすべて満たす変更は、`/quick-change` の軽量フローで進められます（正本は WF-14〜16）。

- 新しい要件の追加や受け入れ基準の変更がない
- 公開インタフェースの追加・変更がない
- 作成・変更するファイルが3つ以下

流れは「探索 →（不具合なら）再現テストで Red を確認 → 修正 → テスト・リント・ビルド → コードのレビュー」です。資料だけの変更はテストを省き、計画書のレビューだけを行います。途中で条件を満たさなくなったら、4.5 の変更要求に切り替えます。

### 4.5 機能の追加・仕様の変更・機能の削除（開発開始の後）

一度できたプロジェクトに、新しい要件の追加、既存の受け入れ基準の変更、機能の削除、構成（architecture.md）の変更が入るときは、`/plan-spec change <変更内容>` から始めます（正本は WF-18・19、PLAN-22〜25）。

1. **変更要求の計画**: Claude が影響一覧（変える REQ、その REQ に紐づく DES、その DES のテスト、影響する資料の見出し）を作り、REQ を追加・改訂・削除して、変更分の実装順を決めます。目的やスコープが変わる場合は、overview.md の改訂点だけを質問します。計画書のレビューの後、影響一覧と実装順を承認します。
2. **設計**: 影響を受ける要件ごとに `/plan-spec REQ-xxx` で設計します。既存の振る舞いを変える・なくす場合は、新しい設計を足さずに既存の DES を改訂します。同じ振る舞いの説明が1か所に残り、テストに書いた `DES-001 #1` の参照も切れません。
3. **実装**: 設計1つごとに `/implement-tdd` で実装します。既存のテストを変更・削除できるのは、設計の「既存の振る舞いへの影響」に書いた振る舞いのテストだけです。振る舞いを削除するだけの設計は、テストを書かずに削除し、全テストの成功とコードのレビューで確かめます。

変える要件も設計も1つだけの小さな変更要求は、計画から実装までを1つのタスク記録で進められます。

### 4.6 リンター・フォーマッター

- フォーマッターは、Claude がファイルを編集するたびに hook が自動で実行します。リンターは、テストと同じ検証のステップで実行します。
- hook は技術・環境の資料（`docs/project/tech.md`）の「開発コマンド」表にある「フォーマット（1ファイル指定）」と「フォーマット対象の拡張子」の行だけを読むため、言語に依存しません。未記入か「なし」のあいだは何もしません。
- 使うツールは開発開始時に選び、技術・環境の資料に書きます。

### 4.7 資料の更新ルール

資料は作って終わりではなく、継続的に更新します。主な方針は次のとおりです。ルールの正本は [`docs/guidelines/documentation.md`](docs/guidelines/documentation.md) です。

- その場で上書き更新し、過去の内容は git 履歴で追います。判断の経緯は ADR に残します。
- 同じ情報は1か所にだけ書きます（SSoT）。1ファイルには1つの責務だけを持たせます。
- 例外として、タスク記録の「作業ログ」だけは追記します。

### 4.8 AI への資料の読ませ方

| 仕組み | 役割 | docs の読ませ方 |
|---|---|---|
| `docs/guidelines/` | 基準（ルール、観点、定義）の正本 | — |
| CLAUDE.md | 落とし穴と索引 | 作業ごとに読む資料をポインタで示す（`@` インポートはしない） |
| Skills | 手順 | 手順の最初で、該当する guidelines を読む（同じ会話で読み済みなら省く） |
| agents | 役割、使えるツール、出力形式 | 定義の本文で、判定に使う guidelines を読む。毎回新しいコンテキストで起動するため、読む資料の範囲を review.md の「対象別の判定基準」に絞る |
| hooks | 機械的な強制 | 読ませない（読まなくても守られる部分を担当する） |

guidelines の各ルールには ID（例: `TEST-03`）を振ります。レビューの指摘には違反したルール ID を必ず書くため、基準を読まずに出した指摘は検出できます。

### 4.9 外部サービスとの連携

- GitHub は `gh` CLI で操作します。GitHub の MCP サーバーは使いません。
- MCP サーバーは `.mcp.json` に Context7 だけを置きます。初回の起動時に、使ってよいかの承認を求められます。
- Web 検索とページの取得は、Claude Code 組み込みの WebSearch / WebFetch を使います。

| サーバー | 用途 |
|---|---|
| Context7 | ライブラリやフレームワークの最新ドキュメントを調べる。API キーは任意で、なくても使える（レート制限が厳しくなる） |

### 4.10 hooks

`.claude/settings.json` に4つの hook を設定しています。スクリプトは `.claude/hooks/` にあり、実行には bash が必要です（Windows では Git Bash か WSL）。jq はあれば使い、なくても動きます。

| hook | タイミング | 内容 |
|---|---|---|
| session-start | セッション開始、再開、`/clear`、圧縮の後 | 進行中・中断中の TASK の「現在のフェーズ」と「次の一手」を Claude に渡す |
| freeze-guard | ファイル編集と Bash の実行の直前 | 進行中・中断中の TASK の `frozen_tests` にあるファイルへの書き込みを止める |
| branch-guard | Bash の実行の直前 | `main` と `develop` への直接のコミット・マージ・プッシュを止める（GIT-02）。`origin` がないときのマージ（GIT-33）と `--ff-only` は通す |
| format | ファイル編集の直後 | 技術・環境の資料にあるフォーマットコマンドで、編集したファイルを整形する |

`claude` はリポジトリの直下で起動します。`.claude/settings.json`（hooks を含む）は起動したディレクトリの `.claude/` からだけ読まれるため、サブディレクトリで起動すると hooks が動きません。スクリプトは Claude Code が設定する `$CLAUDE_PROJECT_DIR`（セッションを開始したディレクトリ）を起点にファイルを探します。

ファイルの編集は Edit / Write ツールで行うことを CLAUDE.md の禁止事項にしています。freeze-guard は Bash のコマンドも見て、凍結ファイルの名前と書き込みの形（リダイレクト、`sed -i`、`mv`・`cp`・`rm`、`git checkout`、スクリプトからの書き込みなど）を両方含むものを止めます。コマンド文字列での判定なので、変数で組み立てたパスなどは見抜けません。その分はコードのレビュー（REV-24）で、凍結コミット以降のテストファイルの差分を検出します。

### 4.11 権限

権限モードは指定せず、Claude Code の既定（v2.1.283 以降は auto モード）に任せます。`.claude/settings.json` には次の3種類のルールだけを書きます。

| 種類 | 対象 |
|---|---|
| 禁止（deny） | `.env` 系ファイルの読み取り（`.env.example` は除く）、`git push` の強制上書き、`git rebase`、`git commit --amend`、`gh repo delete` |
| 確認（ask） | `gh pr merge` |
| 許可（allow） | `git push`（`main`・`develop` へのプッシュは branch-guard が止める）、`bash .claude/scripts/ci.sh`、`gh pr checks`、Context7 のツール |

### 4.12 Git の運用

正本は [`docs/guidelines/git.md`](docs/guidelines/git.md) です。要点は次のとおりです。

- **ブランチ**: 常設は `main`（リリース済み）と `develop`（統合先。GitHub の既定ブランチ）。作業は `develop` から切る `feature/` で行い、リリース済みの本番の緊急修正だけ `main` から `hotfix/` を切ります。`release/` ブランチは使いません。
- **単位**: 1つの要件の設計と全実装で1ブランチ・1 PR です（開発開始と要件定義で1本、変更要求は計画から全実装まで1本、軽微な変更と全体点検は1件ごとに1本）。タスク記録の単位は変わりません。
- **コミット**: タスク記録を更新する区切り（凍結、Green、レビュー合格、承認など）でコミットします。形は `feat(DES-003): 日本語の要約` です。履歴は書き換えません（凍結コミットのハッシュを残すため）。
- **マージ**: すべてマージコミットです。全要件が終わったら `develop` を `main` にマージし、版のタグを付けます（2.9）。
- **CI**: GitHub Actions が、下書きでない PR と `main`・`develop` へのプッシュで `.claude/scripts/ci.sh` を実行します。ci.sh は技術・環境の資料の開発コマンド（インストール、フォーマット、リント、ビルド、テスト）を順に実行し、テストを書けば自動で対象になります。開発開始の前は全体を飛ばします。言語の実行環境の準備は、開発開始（`/kickoff`）で Claude が ci.yml に書きます。Claude はマージの前に CI の成功を確かめます（GIT-24・25）。
- **イシュー**: 使いません。依頼はチャットで受け、記録はタスク記録だけにします。
- **GitHub を使わない場合**: PR の代わりに手元でマージし、差分リンクの代わりに `git diff --stat` を示し、CI の代わりに手元で ci.sh を実行します（GIT-25・33）。

## 5. Claude とのやり取り

- 応答言語は日本語に固定します（`.claude/settings.json` の `language`）。
- Claude からの質問は、1回に1問ずつ提示されます。質問が2問以上になるときは、最初に「全部で何問あり、それぞれ何を聞くか」の一覧が示され、各質問に `2/5` のような通し番号が付きます（PLAN-26）。
- 応答は「である調」で書きます（規則の正本は CLAUDE.md）。
